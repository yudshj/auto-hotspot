# 自动开关热点：预期行为与决策

2026-10-22 与用户确认。代码里的权威版本是 `AutoHotspotCore` 的类注释，
可执行的规格是 `app/src/test/java/dev/autohotspot/SpecScenarioTest.kt`。

## 核心规则

| | 「任意 Wi-Fi」开 | 「任意 Wi-Fi」关 |
|---|---|---|
| **断开 Wi-Fi** | 打开热点 | 打开热点（断开**任何** Wi-Fi 都开，与列表无关） |
| **连上 Wi-Fi** | 关闭热点 | 只有连上**列表里的** Wi-Fi 才关闭 |

前提：「自动开关热点」一个总开关同时控制两个方向（2026-10-22 用户决定：原来「连接 Wi-Fi 时关闭热点」「断开 Wi-Fi 后自动打开热点」
两个开关合并——这本来就是这个应用要做的事，拆开只会组合出半自动状态）。没有 Shizuku 时只能关、不能开（「修改系统设置」只能关）。
「实时监听」「开关热点时发通知」是它下面的子选项，总开关关掉时置灰。

## 用户确认的决策

1. **断开时没有移动数据（流量关 / 没信号）**：先不开热点；等流量恢复、且期间没有连回 Wi-Fi，再**及时**打开。
   流量恢复前就连回了 Wi-Fi，就不再开。
   - 否决：「不开，之后也不补开」；「不管有没有流量都立即开」（没有上游网络的热点没用）。
2. **只在连上/断开的那一刻动作**：用户之后手动改了热点状态，应用不改回去。
   - 在流量下手动关掉自动打开的热点 → 不再打开。
   - 连着 Wi-Fi 时手动打开热点 → 不关（打开应用界面、周期检查也不能关）。
   - 否决：「持续保持状态」（手动改了也会被改回）。

## 沿用的默认（已告知用户，未反对）

- 断开后 5 秒内连回（漫游、路由器短暂掉线）不算断开。
- 用户手动关掉 Wi-Fi 也算断开。
- 连着 Wi-Fi 但读不到 SSID（没有位置权限）：任意模式照样关；非任意模式不关（无法判断是否在列表里）。
- 断开时系统还在自动重连、握手但还没真正连上，算断开（2026-10-21 的 bug：connectionInfo 在握手期间已有 SSID，被误判为「还连着」）。
- 重连是一次新的「连上」：重新连上同一个 Wi-Fi 也按连上处理；再短的连接（例如连上 1 秒又断开）也算一次连上 + 一次断开。
- 连上没有互联网的 Wi-Fi（未验证）也算连上。

## 模糊测试中定下的决策

- **开机算重新开始**（2026-10-22 用户同意）：关机前没处理完的断开不再补做（否则在家重启、移动数据比 Wi-Fi 先连上时会先开热点再关掉）。开机后第一次连上/断开起照常工作。
- **等流量期间用户手动开关过热点**（待用户确认）：流量恢复时照样打开。应用在后台收不到热点状态变化（`WIFI_AP_STATE_CHANGED` 不投递给后台应用），也符合决策 1「流量恢复后再开」。

## 常驻服务与 Shizuku（2026-10-22 调研）

Shizuku 服务端（13.6.0，`ShizukuService` / `BinderSender`）推送 binder 的时机：
服务端启动时推给所有申请了权限的应用；之后每出现一个新进程（新 pid）、或 uid 从缓存/空闲变成活跃时再推。
所以「单进程常驻服务」确实有风险：开机时如果错过了推送（本机 10-21 16:54 就出现过「开机：Shizuku 尚未运行」），
常驻服务让进程和 uid 一直活着，之后再也不会有新的推送。

**采用的做法（2026-10-22，用户同意，开关默认打开）**：「实时监听」开关。
- `MonitorService`：前台服务（`specialUse`），独立进程 `:monitor`，用 NetworkCallback 跟踪「当前 Wi-Fi 连接」和
  「默认网络是不是移动数据」，一变就发广播给主进程的 `CheckReceiver` → `AutoHotspotCore.onCheck()`。
  不读写 SharedPreferences（不支持多进程），日志只进 logcat。
- **Shizuku binder 的流转（真机上踩过坑）**：起初以为主进程被回收后重新拉起（新 pid）就会收到推送，真机上不会——
  实时监听让 uid 一直活跃，新进程等了 8 秒也没有 binder，自动开热点失败。现在 `ShizukuProvider` 放在常驻的 `:monitor`：
  服务端推给它；主进程启动时向它要（`requestBinderForNonProviderProcess`，同步）；之后的推送它会广播给主进程；
  主进程手里有 binder 时也回存给它（`:monitor` 单独重启后手里没有，`CheckReceiver` 每次都会回存）。见 `AutoHotspotApp`。
  多进程支持必须在 `Application.attachBaseContext` 里开启（早于 ContentProvider 初始化）：在 `onCreate` 里开的话，
  Shizuku 的推送可能先到，`:monitor` 收下却不广播，主进程界面误报「需要 Shizuku」（真机上遇到过）。
- 开关热点仍在主进程。
- 原来的 JobScheduler / PendingIntent 机制全部保留，作为实时监听被关掉或被停止时的后备；几路事件来源靠
  `handledWifi` / `lastSsid` 和一把锁去重。
- 实时监听被用户在「活动应用」里停掉后：打开界面、开机、应用更新时重新启动；周期任务也会尝试拉起
  （后台启动前台服务只有在电池白名单里才允许）。
- 常驻通知用最低重要性渠道「实时监听」，用户可以在系统设置里关掉显示。

## 「及时」的含义

事件发生后 15 秒内完成（5 秒防抖 + 任务启动 + 等待 Shizuku + 开/关热点）。
依赖 15~30 分钟一次的周期任务才补上的情况算 bug，周期任务只是最后的兜底——下面列出的已知限制除外。

## 已知限制（只在「实时监听」关着或没在运行时存在）

实时监听在运行时，模糊测试里一次晚处理都没有（断言为 0）；下面这些限制只在它关着或被停掉时出现。

背景：不用常驻服务，只能靠 PendingIntent 网络回调（每次注册只投递一次，约 5 秒后被系统释放）和 JobScheduler（只能按「默认网络」等条件触发）。

1. **连着没有互联网的 Wi-Fi**（默认网络仍是移动数据）时，它断开不会改变默认网络，没有任何事件。
   改为每分钟检查一次（`JOB_RECHECK`），断开后最长约 1 分钟才开热点。
2. **没有移动数据时，Wi-Fi 断开/换到另一个 Wi-Fi 完全没有事件**（默认网络从 Wi-Fi 变成「无」时 JobScheduler 不会触发）。
   新连接要等下一次周期任务（15~30 分钟）才发现；连接在那之前就断开的话，应用根本看不到它。
   影响：流量关着、热点开着、直接换到列表里的 Wi-Fi 时，热点最晚 30 分钟后才关，期间手动打开的热点也可能被这次补做关掉。
   不做每分钟轮询：流量常关、长期连着家里 Wi-Fi 的用户会一直被唤醒，代价远大于收益。
3. **不在电池优化白名单**时，锁屏进入 Doze 后普通任务（定时检查、周期任务；加急配额用完时连「等移动数据」也是）只在维护窗口运行，以上延迟可能再多约 1 小时。
   在白名单里（权限页「电池不受限制」）时 Doze 不影响。

- `SimSystem`（测试代码）模拟 Wi-Fi / 移动数据 / 热点 / JobScheduler / PendingIntent 网络回调 / Doze / 重启，
  用虚拟时间驱动真实的 `AutoHotspotCore`。它建模的系统行为写在类注释里，改动时要和真机实测保持一致。
- `SpecScenarioTest`：按上面的规则逐条写的场景测试。
- `FuzzTest`：随机事件序列（走远/走近、自动重连握手、Wi-Fi 无互联网、流量/信号、锁屏 Doze、手动开关热点、打开界面、重启），
  参考模型按上面的规则推出「此刻热点应该开还是关」，在每个稳定点对照，并检查应用动作不违背预期、不空转。
  已知限制导致的晚动作允许但单独统计。默认 5000 个种子（约 4 秒）；深度跑调到 30000。
- 规格测试在「实时监听」关着（`SpecScenarioTest`）和开着（`SpecScenarioRealtimeTest`）两种情况下都跑。
- 模拟器也建模了实时监听、系统回收主进程、用户停止应用；被杀进程之后的写入不生效（贴近真实的进程死亡）。
- 变异测试（2026-10-22）：把修掉的 12 个 bug 逐个放回去，测试都能发现。

## 真机测试（2026-10-22，Pixel 11 Pro Fold，Android 17 / SDK 37，Shizuku 13.6.0，debug 包）

| 场景 | 结果 |
|---|---|
| 锁屏，关 Wi-Fi（模拟断开），流量开着 | 9 秒后热点打开（5 秒防抖 + Shizuku 约 3.6 秒），之后保持开着 |
| 锁屏，Wi-Fi 重新连上 | 连上后 0.24 秒关闭热点（Wi-Fi 重连本身锁屏时要约 1 分钟） |
| 流量关着时断开 Wi-Fi，30 秒后打开流量 | 30 秒内不开；流量打开后 10 秒打开热点 |
| 自动打开后手动关掉，再来回切换流量 | 不再打开 |
| 应用更新后 | 实时监听自动重新启动 |
| 深度 Doze（强制 force-idle、模拟拔电）+ 移出电池白名单，断开 / 连上 Wi-Fi | 10 秒打开；连上后 0.2 秒关闭 |
| 主进程被 SIGKILL（模拟系统回收），再断开 Wi-Fi | 修复前：新主进程拿不到 Shizuku binder，打开失败；修复后 10 秒打开 |
| `:monitor` 被 SIGKILL（主进程活着），再杀主进程、连上 Wi-Fi | `:monitor` 2 秒后自动重启并从主进程拿回 binder；新主进程连上后 0.1 秒关闭 |
| 实时监听关掉、两个进程都杀掉（后备路径），断开 / 连上 Wi-Fi | 10 秒打开；连上后 0.27 秒关闭 |
| release 包冒烟（断开 / 连上） | 10 秒打开；连上后 0.24 秒关闭 |
| 开机 | 未测：非 root 的 Shizuku 重启后要手动重新启动，没有征得同意不重启 |

**真机上发现的 bug 1**：开热点时系统会建一个传输类型为 WIFI、只有 LOCAL_NETWORK 能力（没有 INTERNET）的网络
（`ap_br_wlan2`）。快照只看传输类型，把它当成「新连上的 Wi-Fi」，刚开的热点 0.3 秒后就被关掉。
修法：`WifiMonitor.wifiRequest()` 是「连着 Wi-Fi」的唯一判定，监听、实时监听、快照都用它（`canBeSatisfiedBy`）。
模拟器没有建模这个网络——它属于 Android 适配层，不在 `AutoHotspotCore` 里。

**真机上发现的 bug 2**：实时监听让 uid 一直活跃后，被回收再拉起的主进程拿不到 Shizuku binder（见上面「Shizuku binder 的流转」）。
同样在 Android 适配层，模拟器测不出来。

## 模糊测试找到并修掉的 bug（2026-10-22）

| bug | 修法 |
|---|---|
| 连着没有互联网的 Wi-Fi 时每 5 秒空转一次（任务立即运行 → 防抖 → 重新注册 → 立即投递 → …），还刷日志 | 连着但不是默认网络时改成每分钟检查 |
| 重新注册监听时系统会把当前连接再投递一次，被当成新的「连上」：打开应用界面、上面的空转都会关掉手动打开的热点 | 记住已处理的连接（Network 句柄），重复投递不动作 |
| 防抖结束那一刻恰好没移动数据，「等移动数据」任务已被消耗，要等周期任务（最长 30 分钟） | 这种情况重新安排「等移动数据」任务 |
| 关机前没处理完的断开在开机后被补做 | 开机清掉 |
| （实时监听）断开还在防抖时又短暂连上一个 Wi-Fi，轮到处理时它已断开却照样关热点，「开 → 关 → 开」来回闪 | 处理「连上」时先确认连接还在，不在就只记录 |
| 处理到一半进程被杀（例如用户停止应用），「已处理」已经记下，之后不再补做 | 做完才记「已处理」 |
